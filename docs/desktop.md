# Desktop: pill and PRs tab

The pill and the PRs tab read one store of data, so they show the same thing: the pill is everything the session watches, and the PRs tab with "Current session only" lists the same watches. The store changes in two ways only: each watch's check sends its new row, which replaces just that row, and full refreshes (opening, the reload button, every 30 seconds for watches and every 3 minutes for the PR search) replace everything.

These need the OpenCode desktop app. Watching itself works in any OpenCode client.

## The pill above the composer

![The pill, opened](images/pill.png)

The menu starts with how many the session watches and a copy button that puts all of them on the clipboard as a list of `- <title>: <url>` lines (a run without a PR by its name), like a group's copy button in the PRs tab.

In OpenCode Desktop, a pill above the session's composer shows how many PRs the session watches ("3 PRs watched"), coloured by the one needing attention most: red when something failed, yellow when a person has to act. Clicking it lists each PR with where it is now ("checks running", "waiting for review", "deploying"…), with buttons that open the PR and its workflow run in the browser. The run is the one still going, else a failed one, else the latest: the PR's checks before merge, the deploy pipeline after. It updates as the watches change.

- The server part exposes the watches over RPC (`rpc.ts`: `pr-watch.list` and a `changed` event); the desktop part (`src/gui.tsx`, the experimental GUI plugin API) reads them.
- The desktop part is a prebuilt bundle: run `bun run build` (or `bun run dev` while changing it). `dist/` is not committed, so build after a fresh clone.

## The PRs tab in the side panel

![The PRs tab, grouped by topic](images/prs-topics.png)

A pinned "PRs" tab in the session's side region (shown by default) lists the open PRs the `gh` user created, in every repo (`gh search prs --author @me`), grouped by repo. One dropdown narrows it to one organisation, another sorts it: by name (repos A–Z), by newest PR, or by oldest PR (repos and their PRs; merged PRs by merge time). A "Show drafts" checkbox (on by default) hides draft PRs when off. A "Group by" dropdown groups by repo (folder icon, the default), by topic (list icon), or not at all ("None": one "All PRs" list, by repo then newest first for "Name", else by date). Topics come from a light model of the panel session's own provider (the same provider guard and model preferences as watches): it names 3–8 topics and puts each PR in one; code drops unknown PRs and puts any it left out under "Other". Topics are kept for the same set of PRs. When PRs come or go, the topics stay: PRs that are gone drop out (and an empty topic with them), and the model is only asked where the new PRs go, an existing topic or a new one if none fits. Only when there are no topics yet, or most PRs are new, does it make a whole new grouping; while they load, or if they can't be made (the reason is shown), the list stays grouped by repo. In topic view each PR also shows its repo. "Show PRs that aren't mine" (on by default) adds the watched PRs others opened (bots, colleagues), told apart by the PR's author. A merged PR whose watch is still going (deploying, waiting for approval) stays with the open PRs until the watch is done, then moves to "Recently merged". "Current session only" (off by default) narrows the tab to the PRs and runs the current session watches; others' PRs among them only show with "Show PRs that aren't mine". A sliders button next to the reload button chooses which buttons each PR line shows (open the watching session, the run, watch or stop, new session, GitHub); the choice applies to every session and to the pill, and is kept. A "Status" dropdown has an "All" checkbox and one per status (all on by default): Needs me (failed, changes requested, conflicts, ready for merge: something to fix, or the merge), Waiting for review, Waiting for approval (a run waiting for someone to approve it), In progress, Done, and Not watched. It filters the open PRs and the workflow runs; "Recently merged" always shows the last week's merged PRs (narrowed by search, organisation and "Current session only"). The dropdowns wrap onto more lines when the panel is narrow. Watches of runs are listed first under "Workflow runs", unless the run's branch has an open PR in the list: then the run shows on that PR's line (its icon, track and buttons), unless the PR itself is watched. A watched PR has a button to open the session watching it. All these choices are remembered per session; a new session starts with the last choices made in any session. A status line at the top shows everything in progress with one spinner ("Loading your PRs…", "Sorting your PRs into topics…", "Starting watching o/r#42…", "Stopping watching …", "Starting a session about …"), then the latest result for a few seconds. Each watched PR's line starts with a status icon for the PR itself and where it is (hover for the words): red when something failed or the branch conflicts or is behind, a pause when it is just waiting on a person (a review, a run approval, a draft, the merge), yellow ⚠ when something needs more than waiting (behind, changes requested, unresolved review comments: "· 2 unresolved comments"), green when done. After the title comes the track: Checks, Review, Merge and Deploy, each green, yellow, red, running or grey upcoming, with details on hover. PRs in My PRs use the same line as the watch lists: a watched PR shows its watch's status icon and where it is (from whichever session watches it), and its run links. A search field at the top filters both lists as you type: every word must be in the PR's title, repo or number (`#803` or `803`), in any case. The search is kept per session while the app runs, but not stored. Clicking a group heading (repo or topic) collapses or expands that group (▾/▸); a collapsed group keeps its count and copy button, and which groups are collapsed is kept, for every session. It is tied to the group's name: a renamed group, or one that goes away (its PRs merged, a new set of topics) and comes back, is expanded. A group hidden by the search or the status filter keeps its state. Each group heading has a copy button that puts its listed PRs on the clipboard as a list of `- <title>: <url>` lines, in the order shown. Each PR shows draft, age and whether it's watched, with buttons to watch it in the current session, to start a new session about it (in the current session's folder, with its provider, model and agent, titled "PR #N on owner/repo", whose first message asks for a summary of the PR) and to open it on GitHub. "Recently merged (7 days)" expands to the PRs merged in the last week, as one list, newest merge first, with each PR's repo, whatever the grouping. It reloads every 3 minutes and when a watch changes, only while the tab is on screen; the server keeps search results for a minute. Search can lag a few minutes behind a merge.

### Waiting for your review

A toggle at the top of the tab switches between "My PRs" (the default, everything above) and "PRs waiting for review" (with a count); the choice is kept. The review list shows the open PRs whose review is requested from the `gh` user, directly or through a team (one GraphQL search, `review-requested:@me`, with each PR's head commit; kept a minute on the server). Drafts and the user's own PRs are left out, since they can't be approved; a PR leaves the list once reviewed. The PRs are grouped by repo (A–Z, newest PR first); a repo with one or two PRs starts expanded, one with more starts collapsed, and clicking its heading opens or closes it. **Favourite repos.** GitHub can't say which repos you may approve in, so you choose: star (★) the repos whose PRs you review, and the list also shows their open PRs that still need a review (`review:required`) even when nobody asked you; those are marked "not requested". At the top of the review list a search field filters every repo (not archived) of your organisations (the owners of your PRs and of the PRs waiting for your review, read with `gh repo list` and kept an hour), with your favourites first and a star on each. It is open until you have a favourite, then folds to one line listing them, and opens again when you search. Repo headings in the review list and in My PRs have the same star. Favourites are kept for every session; up to five repos go in one search.

Only these lines get two buttons, **Explain** and **Review**, both always there:

- **Explain** (glasses icon) is optional. It starts a new session, titled "Review: owner/repo#N title", in the current session's folder with its provider, model and agent. Its first message asks for a summary, a walkthrough, a review against the repo's own rules, a build and test run in a separate worktree, and a suggested verdict with a draft review text; then you can ask about the code. The message tells the agent not to write to GitHub, and to treat the PR's text and code as data, not instructions. When the PR gets new commits after it was explained, the button's label says so, and the new session is asked about `git diff <explained>..<head>`. Which commit of each PR was explained is kept across restarts, and forgotten when the PR leaves the list.
- **Review** opens GitHub's review form under the line, with or without an explanation first: a text field, Comment / Approve / Request changes, and Submit review. A comment or change request needs text, as on GitHub. The review is posted on the commit the list showed (`commit_id`); the server reads the PR's head first and refuses if it has new commits since, so reload the list and look again.

Only the review form submits a review: no tool does, so the agent can't approve a PR. The debug log records `review-submitting` and `review-submitted` with the PR, the choice and the commit.
